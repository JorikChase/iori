# 07 — Control fields, strand flow, editing, and the ID as a dataset (design, 2026-09-12)

Agreed direction from iori: the procedural iris must carry the full breadth of colour and its real shapes, strand directions and warps must come from the photo and be editable by hand (a drag-vector brush), and every eye we fit or make must be stored as weights that reproduce the exact configuration and rendering from a file — while those weights become the ground truth for a later, model-assisted way of making irides. This chapter fixes the representation, the generator that consumes it, how the photo fills it, how a person edits it, and the file that stores it. Implementation follows in the order at the end.

## 1. Representation: globals + objects + control fields

The iris ID grows from *globals + object lists* (§9.1 of the spec) to **globals + objects + control fields**. A control field is a small grid over the polar domain (u = angle, v = tissue radius, 0 at the pupil edge, 1 at the limbus), bicubically upsampled in the bake. It is not an image: it holds *parameters* of the generator, the fine detail beneath it is still generated.

Two grid resolutions, both fixed so the stack has a fixed shape (which is what a learned model needs later):

| grid | size | cell (ciliary zone) | used for |
|---|---|---|---|
| control | 128 × 32 | ≈ 0.2 mm × 0.125 mm | material, weights, presence |
| flow | 256 × 64 | ≈ 0.1 mm × 0.06 mm | strand direction, warp, spacing, phase, brightness |

### Fields (channels)

| field | grid | type | meaning |
|---|---|---|---|
| `melanin`, `yellow`, `pheo`, `stroma` | control | u8 → range | material of the **strand** at this place (02 §4 + the yellow absorber) |
| `gapMelanin`, `gapStroma` | control | u8 | material of the **gap** between strands (dark ground); the two-material split measured in 06 |
| `strandBright` | flow | u8 | ridge brightness / contrast of strands (06: ridge/gap ≈ 4× linear where 1.0) |
| `spacing` | flow | u8 → 0.02–0.15 mm | local strand spacing (06: 35–70 µm) |
| `flowDir` | flow | i8 → ±60° | strand direction as a deviation from radial |
| `warp` | flow | 2 × i8 → ±0.5 mm | displacement of the strand pattern (the "comb" / liquify field) |
| `phase` | flow | u8 → 0–2π | phase of the strand pattern across the flow; lets strands land where the photo's do |
| `coherence` | flow | u8 | how ordered the strands are (blur / interruption of the pattern) |
| `crypt`, `furrow`, `radialFurrow` | control | u8 | presence / depth multipliers for the object generators |
| `collarette` | control | u8 | presence and frill weight along the collarette (the spline gives its position) |
| `height` | control | i8 → ±0.1 mm | relief offset on top of the generated height |

Everything not listed stays as it is: globals (indices, exponents, defaults), objects (crypts, furrows, spots, nodules, bundles, the collarette spline), view (pose, light, camera).

### Objects that carry colour

Bundles get `pigment` (multiplier on the strand material) and `pigmentExtent` (v up to which they carry pupillary pigment): this is the star-shaped amber region of ref 25 — pupillary pigment carried outward along particular bundles. Crypts keep their own depth; the gap material shows in them.

### The collarette

A closed spline of 24–48 control points (u, v) with per-point frill amplitude and height. The Fourier series of §12 becomes derived (for the fitter's smooth parametrisation), the spline is what is stored and edited. Globals: width, height, feathering; bundles terminate at it.

## 2. Generator: strands from the flow field

The strand layer is generated by **line integral convolution (LIC)** of high-frequency noise along the flow field: for every atlas texel, integrate noise along the local strand direction (± ~16 steps of one texel), which yields streaks that follow `flowDir` with the noise's frequency across it. `spacing` sets the noise frequency, `phase` shifts the pattern so strands sit where the photo's do, `warp` displaces the sampling position (domain warping by the field), `coherence` mixes in an uncorrelated term, `strandBright` scales the ridge profile. The bundle objects remain as slow modulators (brightness, width, branching) on top of the field. The seeded Worley field of §12 is retired.

Two-material shading: the ridge profile of the strand layer is the mix weight between the strand material and the gap material per texel (both looked up through the spectral LUT), with contact shadow in the gaps and an anisotropic sheen along `flowDir`. Targets: 06 — ridge/gap L* 49/24, local contrast 0.31–0.37, dark coverage 12–14 %.

## 3. From the photo: estimating the fields

All on the unwrapped photo (through the engine's forward path once §9.2 step 3 is done; through the photo-geometry unwrap until then).

- **flowDir, coherence**: structure tensor per flow cell (Gaussian-smoothed products of gradients); dominant orientation → direction, eigenvalue ratio → coherence. Robust and standard.
- **spacing**: dominant angular frequency per cell from a windowed spectrum (the 06 method, localised).
- **phase**: phase of a Gabor response at the local frequency and orientation, per cell.
- **warp**: integrated deviation of the orientation from radial, i.e. how far the pattern has been combed sideways; alternatively fitted after the fact by minimising the residual between the LIC result and the photo strip.
- **strandBright, material fields**: per control cell, separate ridge pixels from gap pixels (local maxima / minima along the angle, 06), take their median Lab, and invert the spectral LUT to (melanin, stroma, pheo, yellow) for the strand and (gapMelanin, gapStroma) for the gap. A precomputed inverse table on Lab makes this instant.
- **crypt / furrow / collarette fields**: the detectors of §13, written as presence weights rather than only objects.
- **collarette spline**: minimal-cost closed path in polar space by dynamic programming over a cost image built from three cues — brightness ridge, colour transition (pupillary → ciliary material), change of strand frequency — with a smoothness penalty. The spline snaps to the path.

## 4. Editing: brushes on the polar canvas and on the eye

EDIT mode shows the polar canvas enlarged (photo strip optional underneath, live render strip). Tools act on a selected field:

- **Comb** (drag-vector brush): sets `flowDir` toward the drag direction under the brush with a soft falloff; shift-drag adds to `warp` (liquify).
- **Paint / erase / smooth** on any scalar field (material, brightness, presence, height), with pressure = strength.
- **Eyedropper**: sample the photo's colour under the cursor and set the cell's strand or gap material through the inverse LUT.
- **Points**: drag collarette control points; place / move crypts, spots, nodules, bundles.
- Every edit is a deterministic operation on stored numbers; the bake updates live; undo is a stack of field diffs.

On the eye view the same tools work by projecting the cursor through the engine's forward path to (u, v); polar first, because it is exact and simpler.

## 5. The ID file (v2) and determinism

```
{ v: 2, engine: "<version>", seed,
  globals: {...}, objects: { coll: {points, frill, height}, crypts, furrows, spots, nodules, bundles },
  fields: { <name>: { w, h, type: "u8"|"i8", range: [lo, hi], data: "<base64>" } },
  view: {...},
  provenance: { photo: { sha256, file, w, h }, alignment, fitVersion, scores, history: ["fit:global", "edit:comb", ...] } }
```

- Sizes: control fields ≈ 4 KB each, flow fields ≈ 16 KB each; a full ID ≈ 150–250 KB. Files, not URLs (the URL keeps `#seed=…` or a short ID).
- **Determinism**: the bake is a pure function of the ID; all noise is seeded from `seed`; the render is a pure function of ID + view. Across GPUs the result agrees to float precision; the file records the engine version and, optionally, a checksum of the reference render so a mismatch is detectable.
- **Fields as a dataset**: because every ID has the same fixed-shape field stack, a fitted eye is a training pair (photo → fields + objects). Export writes `dataset/<id>/` with the photo, the alignment, the ID and the reference render. That is the preparation for a model that predicts fields from a photo directly; the engine stays the renderer either way.

## 6. Implementation order

1. **Field infrastructure**: field store in JS (typed arrays), upload as R8/RG8 textures, bicubic sampling in the bake, ID v2 read/write with base64, the ATLAS viewer showing fields. No behaviour change yet (fields initialised from the current globals).
2. **Strand generator**: LIC along `flowDir` with `spacing`, `phase`, `warp`, `coherence`, `strandBright`; two-material shading; bundles as modulators. Judge in POLAR, score with BENCH ISO against the 06 targets.
3. **Photo → fields**: structure tensor, local frequency and phase, per-cell strand/gap material inversion, presence fields; collarette DP trace → spline. BENCH ISO.
4. **Editing**: polar canvas tools (comb, warp, paint, smooth, eyedropper, points), then on-eye projection.
5. **Provenance and dataset export.**

Decisions taken here (iori can override): a control grid in the ID counts as procedural; editing starts on the polar canvas; LIC is the strand generator; the collarette is stored as a spline.
