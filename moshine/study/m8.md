# M8 — compatibility: findings and how to test

Started 2026-10-10. Exit (spec §13): the core flow works on Safari 26 and Firefox current on macOS; the governor's
caps are shown on an iPhone.

## How to run

```bash
node moshine/tools/xbench.mjs --browser webkit --tag m8          # the whole harness in Playwright WebKit
node moshine/tools/xbench.mjs --browser webkit --only exportMix   # some rows
node moshine/tools/xbench.mjs --browser webkit --shot x.png --size 1440x900   # the editor on ?demo
node moshine/tools/bench.mjs --tag m8-chrome                      # Chrome (DevTools protocol), as before
```

`xbench.mjs` uses the Playwright copy installed for iori's audio tests (`PLAYWRIGHT=` overrides) and its cached
browser builds; nothing is downloaded. Each run gets a fresh persistent profile (WebKit's throwaway contexts have no
OPFS) and its own free port (other sessions run servers on 879x that serve other trees).

## Fixed

1. **Luma rounded differently per compiler.** The float BT.709 dot product gave ULP differences between GPU and CPU
   (about 8,000 pixels at level 0 in Chrome, 10,000 in WebKit). In WebKit a matcher near-tie flipped at frame 5 of
   `cut.mp4` and the loops drifted (`videoCut` 85 % identical). Luma is now exact integer arithmetic on both twins
   (`gpu.js LUMA_WGSL`, `engine-ref.js lumaPx`): channels clamp to [0, 1] at 1/32768, integer weights summing to
   65536. `pyramidParity` is 0 differing pixels; fidelity budgets unchanged (clip mosh SSIM 0.7262 → 0.7261).
   The matcher itself was exact (the CPU matcher on the GPU's pyramids gives the GPU's vectors).
2. **WebKit's AAC encoder description.** `AudioEncoder` (AAC) returns a whole ES_Descriptor (an esds payload, 39 bytes)
   as `decoderConfig.description`. WebKit's own `AudioDecoder` refuses it (`InternalAudioDecoderCocoa decoding failed`)
   and an MP4 would nest descriptors. `export.js cleanAudioConfig` unwraps the AudioSpecificConfig. On the live site
   before this fix, any mixed-audio export failed in Safari.

## Cross-engine determinism

Chrome and WebKit give the same hashes for `moshReplay`, `loopReplay` and the effect loops, so a project renders the
same pixels in both. **Exception: the optical-flow looks ("Fluid")**: the Lucas–Kanade solve divides in floating
point (`flowParityTruth` was never exact: max GPU/CPU 2e-5), and Chrome and WebKit differ. Making flow exact is an
open thread.
