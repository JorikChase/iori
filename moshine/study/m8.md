# M8 — compatibility: findings and how to test

Started 2026-10-10. Exit (spec §13): the core flow works on Safari 26 and Firefox current on macOS; the governor's
caps are shown on an iPhone.

## How to run

```bash
node moshine/tools/xbench.mjs --browser safari --tag m8           # Safari itself (safaridriver, WebDriver classic)
node moshine/tools/xbench.mjs --browser zen --headed --tag m8      # Zen = Firefox's Gecko (WebDriver BiDi); --bin for Firefox
node moshine/tools/xbench.mjs --browser webkit --tag m8           # Playwright WebKit (Safari's engine, newer build)
node moshine/tools/xbench.mjs --browser safari --only exportMix   # some rows; --progress prints each row
node moshine/tools/xbench.mjs --browser safari --shot x.png --size 1440x900   # the editor on ?demo
node moshine/tools/bench.mjs --tag m8-chrome                      # Chrome (DevTools protocol), as before
```

- Rows run one script call each (a whole run in one call hits safaridriver's HTTP timeout) and results land in
  `ref/xbench-<browser>-<tag>.json` with every console error and failed request.
- **Safari** needs `safaridriver --enable` (admin, once) and Develop ▸ Allow Remote Automation (done 2026-10-10).
  An automation window opens while it runs.
- **Zen / Firefox** is launched through LaunchServices (`open -n`) with a fresh profile and its own debugging port:
  started straight from a shell, the app never initialises its profile. `-n` gives a separate instance, so the
  owner's open Zen is never touched; the run kills exactly its own process (found by its port). **Headless Gecko
  has `navigator.gpu` but no adapter**: use `--headed` (the window opens in the background).
- Playwright is borrowed from iori's audio tests (`PLAYWRIGHT=` overrides); nothing is downloaded.

| Zen (Gecko 157) | 1.23.1b | 31 + 10 pass, 0 console errors | 10.1 ms | about 5 ms per submit round trip (wgpu), so readback-heavy rows are slow (`checkpointParity` 103 s against 3 s, a full run 6–15 min); real playback is fine |

error (T1 `exportMix`).

## Fixed on the way

1. **Luma rounded differently per compiler.** The float BT.709 dot product gave ULP differences between GPU and CPU
   (about 8,000 pixels at level 0 in Chrome, 10,000 in WebKit); in WebKit a matcher near-tie flipped at frame 5 of
   `cut.mp4` and the loops drifted (`videoCut` 85 % identical). Luma is now exact integer arithmetic on both twins
   (`gpu.js LUMA_WGSL`, `engine-ref.js lumaPx`). `pyramidParity` 0 pixels; fidelity unchanged.
2. **WebKit's AAC description.** Safari's `AudioEncoder` (AAC) returns a whole ES_Descriptor as
   `decoderConfig.description`; its own decoder refuses it and an MP4 would nest descriptors (`export.js
   cleanAudioConfig` unwraps it). Before this, every mixed-audio export failed in Safari.
3. **Opus was shifted twice in Safari.** Opus carries its pre-skip (312 samples) in the OpusHead and players apply
   it. Safari's `AudioDecoder` ignores pre-skip when probed, so the encoder-delay probe said 312 there (0 in Chrome)
   and the WebM played 6 ms early. Opus is never shifted now; only AAC is (no in-band priming in MP4).
4. **Firefox refuses a VideoFrame as a copy source** (`copyExternalImageToTexture`): the copy rung of the decode
   ladder draws the frame into a canvas first (`media.js`). The zero-copy rung works in Firefox as it is.
5. Harness errors now include the message in every engine (Firefox stacks leave it out).

## Cross-engine determinism

| Loop | Chrome | Safari | Zen | WebKit |
|---|---|---|---|---|
| Xvid classic replay (`moshReplay`) | `9a7a3522` | same | same | same |
| Field ops noise + smooth (`loopReplay`) | `9a06ed2b` | same | **differs** | same |
| In-loop echo + freeze, deblock (`fxLoopReplay`) | — | **differ** (Safari = Zen) | **differ** | same as Chrome |
| Fluid (optical flow) | — | differs | differs | differs |

Each engine is deterministic with itself, and the plain block-matching mosh is identical everywhere. The field ops
`noise` and `smooth`, the M3 effects with fractional mixes (echo, deblock, …) and the flow solve are not
contraction-proof (they were never exact GPU against CPU either: `fieldOpsParity` up to 7e-6, `fxMix` "close"), so
compilers that fuse multiply-adds differently give slightly different pixels. Making them exact (the D28 pattern:
quantised weights, exact products) is the open thread that would make a Mosh ID render the same pixels in every
browser.

## Presentation colour (Safari)

Safari's screenshot of the editor shows the preview paler than Zen's while the UI around it matches. Inside the
page the presented canvas holds exactly the texture's values in both browsers (sampled through a 2D canvas), so the
app outputs the same colours; the difference is in Safari's capture or compositing of the WebGPU canvas. To confirm
by eye: open https://iori.me/moshine/?demo in Safari and in Zen side by side.
