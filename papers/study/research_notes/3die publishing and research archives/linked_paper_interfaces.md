# Interfaces for interlinked papers and notes: how linked writing is visualised and navigated on the web

Scope: techniques for presenting a series of interlinked papers (root paper 0, sub-papers 0.1, 0.2, 0.3 that share a reference list and import each other's code and figures), to decide what the "3die publishing" archive should show: list, tree, graph, backlinks, transclusion or something else. Researched 2026-11-09. URL status was checked with curl on 2026-11-09. Notes: `stacks.math.columbia.edu`, `edwardtufte.com` and `scite.ai` returned 403 to a script (probably bot blocking, so not confirmed dead). `metacademy.org` and `ciechanowski.me` did not resolve. Ciechanowski's real domain is ciechanow.ski, which was not checked.

## Backlinks and transclusion (gwern.net, Matuschak, Wikipedia, Xanadu, Distill, Quartz/Obsidian, Ink & Switch)

### Takeaway
The proven pattern for linked writing has three layers. First, previews in place: hover or tap popups for links, citations and footnotes. Second, backlinks shown with their surrounding context. Third, selective transclusion: embed a section on demand rather than copying it. A global graph is the weakest of these and the most often dismissed. gwern.net is the most complete example of this approach without a graph. It generates its link, backlink and similar-link databases offline, and a small amount of client-side JS loads them lazily.

### Cited Findings
- **gwern.net popups/popins.** Hovering or tapping a link opens a preview. "Annotated" links show a mini-page with metadata and an abstract. Popups can be recursive, moved, resized and pinned. On wide screens sidenotes replace footnotes, and on narrow screens they fall back to popovers. All of this is client-side JS (`popups.js`, `sidenotes.js`). The stated principle is "semantic zoom": readers "drill down as deep as they wish" — [gwern.net/design](https://gwern.net/design)
- **gwern.net annotations.** These are hand-written or auto-extracted (Arxiv/Crossref) summaries of linked sources, kept in a metadata database, so a page's links read like an annotated bibliography — [gwern.net/design](https://gwern.net/design)
- **gwern.net transclusion.** Content from another page or annotation is embedded in place. It is "lazy by default, but can be made strict". Backlinks and tag indexes are built on top of transclusion, which makes very large "virtual" pages possible — [gwern.net/design](https://gwern.net/design)
- **gwern.net backlinks.** Each backlink shows the calling context and can point to a specific anchor or section, because links carry unique IDs. They are generated offline by parsing Markdown and annotation HTML, run as "a cron job at night" because Hakyll is "not a good fit". They are then shown as collapsed, lazily loaded transclusions. Gwern criticises MediaWiki's "what links here" for giving no context. Generating backlinks from the author's own annotations "solves the problem of spam backlinks" — [gwern.net/design](https://gwern.net/design)
- **gwern.net similar links and link bibliographies.** "Similar links" lists about a dozen annotations found by k-nearest-neighbour search over neural embeddings of annotation text. A "link bibliography" lists every link on a page in order with its annotation expanded, and it replaces the usual reference list. Both come from the same link database — [gwern.net/design](https://gwern.net/design)
- **Matuschak's working notes.** The site (live, [notes.andymatuschak.org](https://notes.andymatuschak.org)) opens each followed link in a new column beside the previous ones, so the reader's path stays visible. This is described by third parties ("sliding panes solve context loss") — [hannesdelbeke wiki: sliding panes](https://hannesdelbeke.github.io/wiki/sliding%20panes). Matuschak's own pages read here say nothing about how the site is built — [notes.andymatuschak.org](https://notes.andymatuschak.org/Evergreen_notes_should_be_densely_linked)
- **Matuschak on backlinks.** In a search summary (I did not open the note itself), Matuschak's note calls backlinks a weak "peripheral vision": mainly a way to switch notes rather than make sense of many at once, and they lose object permanence. This is reportedly part of why he uses side-by-side panes — [notes.andymatuschak.org (search result)](https://notes.andymatuschak.org/zsRuFxYgckGS81tr2eiBAP). Verify before quoting.
- **Stacked panes as a reusable component.** Quartz has a "stacked pages" plugin that encodes the stack in the URL hash (`#stacked=slug1,slug2`), so a path through the notes can be shared. A recreation turns stacking off below 800 px — [Quartz stacked pages](https://four.quartz.jzhao.xyz/plugins/stackedpages). Obsidian has a community "Sliding Panes (Andy Matuschak Mode)" plugin — [forum thread](https://forum.obsidian.md/t/andy-matuschak-mode-v2-7-updated-for-0-7-new-panes/170?page=6)
- **Wikipedia Page Previews (hovercards).** English/German A/B tests in 2017–18 found fewer pageviews but more distinct pages interacted with, which reads as broader exploration. Session depth "remained relatively equal", back-button use fell, and only about 0.01% of users turned previews off. The feature is on by default for anonymous users on all Wikipedias since July 2018. Admins set the hover delay; 250 ms is given as an example — [mediawiki.org/wiki/Page_Previews](https://www.mediawiki.org/wiki/Page_Previews). The 2017–18 analysis measured about 0.26 cards viewed per pageview and warned that hovers can be accidental — [Phabricator T182314](https://phabricator.wikimedia.org/T182314). Earlier 2016 tests on Hungarian, Italian and Russian Wikipedia suggested readers chose pages more precisely and paid less to explore — [mediawiki.org/wiki/Hovercards](https://www.mediawiki.org/wiki/Hovercards). Wikimedia's write-up on why the feature took years to ship — [Medium](https://medium.com/freely-sharing-the-sum-of-all-knowledge/why-it-took-a-long-time-to-build-that-tiny-link-preview-on-wikipedia-d5bd734df8fe)
- **Xanadu / Ted Nelson.** Nelson separates links, which "connect parts which are different", from transclusion, which shows "the heretofore-invisible connections between identical parts" (visible re-use). He calls side-by-side parallel documents with visible connecting strips "crucial" — [xanadu.com/xuvision.html](https://xanadu.com/xuvision.html). Maggie Appleton's pattern essay describes visible links as showing the destination's full context and as depending on parallel documents and "transpointing windows" — [maggieappleton.com/xanadu-patterns](https://www.maggieappleton.com/xanadu-patterns). OpenXanadu was put online in 2014 as "a working deliverable" but "not yet open source" — [Wikipedia: Project Xanadu](https://www.wikipedia.org/wiki/OpenXanadu)
- **Distill.** The bibliography is BibTeX inside `<script type="text/bibliography">`. Inline citations are `<dt-cite key="...">` (one key or a comma list), rendered as numbered links that show the reference on hover, and the bibliography is generated into `<dt-appendix>`. Footnotes are `<dt-fn>` and also appear on hover. The guide page shows the older `dt-` tag prefix; later Distill templates use `d-cite`/`d-footnote`, which I did not verify on that page — [distill.pub/guide](https://distill.pub/guide/)
- **Quartz.** The graph is a community plugin (`github:quartz-community/graph`). The local graph shows depth 1 (one hop). The global graph, opened from an icon, shows all notes (`depth: -1`) with force parameters (`repelForce`, `centerForce`, `linkDistance`), node radius from link count, a visited-node colour, and `focusOnHover`. It reads the build-time `contentIndex.json`, and with that index disabled the graph is empty — [quartz.jzhao.xyz/features/graph-view](https://quartz.jzhao.xyz/features/graph-view). Backlinks and popover previews are separate features with their own pages (live): [backlinks](https://quartz.jzhao.xyz/features/backlinks), [popover previews](https://quartz.jzhao.xyz/features/popover-previews)
- **Ink & Switch, Patchwork.** This is version control for writing. Prose was the first domain, with history visualisation, granular "dynamic history" and lightweight branches, and the lab wrote its own notebook in it — [Patchwork notebook 02 · Writing prose](https://www.inkandswitch.com/patchwork/notebook/02), [notebook index](https://www.inkandswitch.com/patchwork/notebook/). A search summary (not opened) says a talk titled "Introducing Patchwork-26", dated 2026-07-14, was the first public release — [inkandswitch.com](https://inkandswitch.com/). Verify before relying on it.
- **Ink & Switch, Jacquard** (Project 031, summer 2024). Billed as "a collaborative environment for writing empirical research papers" that brings writing and data analysis together. The project page does not say whether it handles transclusion or reuse of figures or code across papers — [inkandswitch.com/project/jacquard](https://www.inkandswitch.com/project/jacquard)
- Other live sites from the brief, checked as HTTP 200 but not researched in depth: [Peritext](https://www.inkandswitch.com/peritext/), [TiddlyWiki](https://tiddlywiki.com), [Hypothesis](https://web.hypothes.is), [Obsidian Publish](https://obsidian.md/publish), [Obsidian graph docs](https://help.obsidian.md/plugins/graph), [Logseq docs](https://docs.logseq.com)

### Inferences
- A short numbered series like 0 → 0.1/0.2/0.3 already has a canonical order, so the techniques with the best value for the work are popups on cross-paper links and citations (Distill/Wikipedia style) and context backlinks at section level ("§2.6 of paper 0.3 uses this figure", gwern style). Both can be generated offline from one registry, which matches the existing `site.py` pipeline.
- Nelson's split between links (different parts) and transclusion (identical parts) fits the series closely. A figure or code module that paper 0.3 imports from paper 0 is the identical part, so it can be shown as a transclusion with a visible "from paper 0 §x" source strip instead of a plain link.
- Stacked panes fit papers less well than atomic notes. Papers are long, and the panes switch off on mobile. Popups plus an "open beside" option for desktop gets most of the benefit.
- Peritext and Patchwork concern collaborative editing and history, not reader-side navigation. They matter only if the archive plans to show versions or diffs of papers.

### Gaps
- I did not find Matuschak's own account of how his site is built.
- I did not verify a peer-reviewed study of backlinks or stacked panes on reading comprehension. The Wikipedia A/B tests are the only controlled evidence I found for any of these techniques.
- TiddlyWiki, Roam/Logseq publishing, Hypothesis and Peritext were checked as live only, not described in detail.
- I did not confirm the "Patchwork-26" public release from a primary page.

## Citation and paper graphs: layouts that work and the "hairball" critique

### Takeaway
Literature tools that work treat closeness as meaning and add a second axis or a list alongside: similarity layouts (Connected Papers), a time × citations scatter (Litmaps), cluster bubbles (Open Knowledge Maps). Each also pairs the picture with list views such as Prior/Derivative works. Plain citation-edge force layouts are what get called hairballs. With four papers none of these tools is needed, but they show the encodings readers already know: x = time, colour = year, size = weight.

### Cited Findings
- **Connected Papers** measures similarity with co-citation and bibliographic coupling, not direct citation. Neighbouring papers may not cite each other. The layout is force-directed. Colour shows year (darker means newer) and size shows citation count. Selecting a node highlights its shortest path to the origin paper. "Prior works" and "Derivative works" lists give common ancestors and common descendants — [connectedpapers.com/about](https://www.connectedpapers.com/about); [Connected Papers launch post](https://medium.com/connectedpapers/announcing-connected-papers-a-visual-tool-for-researchers-to-find-and-explore-academic-papers-89146a54c7d4); [LMU libguide](https://libguides.lmu.edu/AIresearchtools/CP). Library guides note a bias toward highly cited papers — [Arizona libguide](https://libguides.library.arizona.edu/ai-researchers/connectedpapers)
- **Litmaps** by default puts publication date on x and citation count on y, with circle size also showing citations. Either axis can be switched to reference count or "momentum" (citations adjusted for recency). A seed map built from a DOI shows citing, cited and similar papers — [HKU blog on Litmaps](https://blog-sc.hku.hk/?p=3264); [Litmaps docs](https://docs.litmaps.com/en/articles/9181490-use-and-edit-litmaps-visualization); [Guide to Litmaps visualisations](https://medium.com/litmaps/guide-to-litmaps-visualisations-95a9bc2cc9de)
- **Open Knowledge Maps** clusters the top 100 results from BASE or PubMed into labelled bubbles on a 2-D map. Closer bubbles mean closer subjects, bubble size reflects the cluster, and labels come from subject keywords — [openknowledgemaps.org/faq](https://openknowledgemaps.org/faq); [HKUST library](https://library.hkust.edu.hk/sc/ok-maps/)
- Live but not researched in depth this session: [ResearchRabbit](https://www.researchrabbit.ai), [Inciteful](https://inciteful.xyz), [VOSviewer](https://www.vosviewer.com), [CiteSpace](https://citespace.podia.com), [Semantic Scholar](https://www.semanticscholar.org), and the arXiv Labs showcase, which lists the bibliographic explorers on abstract pages: [info.arxiv.org/labs/showcase.html](https://info.arxiv.org/labs/showcase.html)

### Inferences
- What these tools share is that their layouts encode a variable the reader can name (time, similarity, cluster), and each pairs the picture with a ranked list. For a four-paper series a timeline with the shared reference list as a column (Litmaps' time axis applied to the series) would earn its place more clearly than a free force layout.
- Co-citation and bibliographic coupling can be computed from a shared reference list. Showing how many references two sub-papers share is a cheap, honest edge weight.

### Gaps
- I found no formal published "hairball" critique of specific literature tools. The critique evidence I have comes from PKM communities (next sections). Layout details for ResearchRabbit, Inciteful, VOSviewer and CiteSpace were not checked this session.

## Series and dependency presentation (prerequisite maps, reading order)

### Takeaway
The strongest examples are formal mathematics: the Stacks Project's tag graphs and Lean "blueprints". Both make a dependency graph from explicit `\uses`-style declarations in the source, colour nodes by status or type, and keep the linear document as the main view, with the graph as an auxiliary page. That fits a paper series with explicit imports.

### Cited Findings
- **Stacks Project.** Every result has a permanent four-character "tag". Since 2013 the site has offered interactive dependency views per tag: force-directed, a collapsible view following the chapter hierarchy, and a cluster view, with nodes labelled by tag and coloured by type — [mathbabe 2013](https://mathbabe.org/2013/07/30/the-stacks-project-gets-ever-awesomer-with-new-viz/). An analysis notes that only dependencies cited directly in proofs are drawn, not every logical edge — [mathbabe 2013 analysis](https://mathbabe.org/2013/07/31/analyzing-the-complexity-of-the-stacks-project-graphs/). A 2016 alternative shows chapters and parts as a chord diagram — [Belmans 2016](https://pbelmans.ncag.info/blog/2016/05/26/alternative-visualisation-of-the-structure-of-the-stacks-project/). Graph pages such as `/tag/0BRR/graph/force` returned 403 to a script, so I could not confirm they are live.
- **Lean blueprints (Patrick Massot's leanblueprint, plasTeX).** The dependency graph is generated from LaTeX macros: `\uses{...}` creates edges and `\leanok` marks something stated or proved. Node colour encodes status (stated, can-state, not-ready, proved, fully-proved, in mathlib). `\graphcolor` sets each colour and its legend text. A node counts as fully proved only when all its ancestors are proved — [Algolia docsearch index of leanblueprint](https://docsearch.algolia.com/mcp/docs/repo/patrickmassot/leanblueprint); [Zulip: Blueprint colors](https://leanprover-community.github.io/archive/stream/423402-PrimeNumberTheorem+/topic/Blueprint.20colors.html); [Zulip: writing the blueprint](https://leanprover-community.github.io/archive/stream/509433-Brownian-motion/topic/Writing.20the.20blueprint.html). Repo: [github.com/PatrickMassot/leanblueprint](https://github.com/PatrickMassot/leanblueprint). Live example: Tao's PFR blueprint graph, [teorth.github.io/pfr/blueprint/dep_graph_document.html](https://teorth.github.io/pfr/blueprint/dep_graph_document.html). Exact hex values came from an index and were not checked against the current release.
- Recent research on this: "KnowTeX: Visualizing Mathematical Dependencies" — [alphaxiv 2601.15294](https://www.alphaxiv.org/abs/2601.15294); "The Network Structure of Mathlib" — [arXiv 2604.24797](https://arxiv.org/html/2604.24797v2); a dependency-graph tooling paper at ITP 2026 — [LIPIcs ITP 2026.25](https://drops.dagstuhl.de/storage/00lipics/lipics-vol382-itp2026/LIPIcs.ITP.2026.25/LIPIcs.ITP.2026.25.pdf) (not read beyond the search snippets). Mathlib stats page (live): [leanprover-community.github.io/mathlib_stats.html](https://leanprover-community.github.io/mathlib_stats.html)
- Book of Shaders is live at [thebookofshaders.com](https://thebookofshaders.com). Its chapter map was not inspected this session. Khan Academy is live, but I did not confirm whether its knowledge map still exists. Metacademy did not resolve on 2026-11-09.

### Inferences
- A blueprint-style `uses:` field per paper or section in `pages.meta.json` (for example `"uses": ["fractals#2.6"]`) is the closest analogue to how the series works now, where sub-papers import code and figures. The graph becomes a by-product of declared dependencies rather than a decoration.
- Colouring by status (draft, hidden, published), as blueprints colour by proof status, would tell readers something a list cannot. The series has a status concept already: 0.1–0.3 are hidden.

### Gaps
- I did not inspect Ciechanowski, Nielsen, Quanta, Khan Academy's map or Book of Shaders for their reading-order patterns. Metacademy appears to be offline.

## Typed links (cites, extends, reuses, refutes)

### Takeaway
Typed edges exist in two forms. One is a formal vocabulary, the CiTO ontology, with dozens of citation intents. The other is coarse colour-coded labels, scite's supporting / contrasting / mentioning, and blueprint node status. Interfaces that show types do it with colour plus the citing sentence, not with edge labels drawn on the graph.

### Cited Findings
- **scite "Smart Citations".** A deep-learning classifier, trained on more than 40,000 hand-annotated citation statements, labels each citing sentence as supporting, contrasting or mentioning, and shows the sentence next to the label. Librarians warn that the classifier is still being refined and that a contrasting label is not a mark of bad science — [CASRAI: scite](https://casrai.org/research-tools/ai-research-assistants/scite); [Manchester libanswers](https://manchester-uk.libanswers.com/OOR/faq/279226); [JMLA review](https://jmla.pitt.edu/ojs/jmla/article/view/1331/1396)
- **CiTO** (Citation Typing Ontology, SPAR) gives a much finer set of citation-intent properties ("dozens of reasons") — [CCC article](https://www.copyright.com/?p=38074). The spec is live at [sparontologies.github.io/cito](https://sparontologies.github.io/cito/current/cito.html). Its property list was not read this session.
- Lean blueprints type nodes by status, and their edges come from `\uses` — see the previous section.

### Inferences
- For four papers, a small fixed set of edge types matches what the series actually does: *extends*, *reuses code*, *reuses figure*, *cites*, and possibly *revises* (from paper 0.3's "where the field stands" chapter). Mapping them to CiTO terms (`extends`, `usesMethodIn`, `usesDataFrom`, `citesAsEvidence`, `disagreesWith`) would keep the data interoperable. This mapping is mine and should be checked against the CiTO spec.
- Show the type in the backlink or popup text ("paper 0.3 §2.6 *reuses the drainage instrument* from paper 0 §4"), not as coloured lines alone. scite shows that the citing sentence carries the meaning.

### Gaps
- I found no interface that draws CiTO-typed edges on a graph for readers, and no evaluation of typed-edge graphs.

## Evidence on usability of graph views

### Takeaway
Controlled studies say node-link diagrams are good at path-following and connectivity in small graphs (about 20–50 nodes), while matrices or lists win for lookup tasks and larger graphs. In practice the "graph view" in note tools is widely called pretty but rarely used: in one informal poll most users said they never use the global graph. Local, filtered or one-hop graphs are the part users defend.

### Cited Findings
- **Ghoniem, Fekete and Castagliola (2004/2005).** Above about 20 vertices, matrices beat node-link diagrams on most readability tasks. Path-finding was the only task where node-link consistently did better — [comparison record](https://opact.sdu.edu.tr/vufind/SummonRecord/FETCH-LOGICAL-c388t-17534b10dd9b1862d94105b93cc92e657f28c5d8e3bcb5b50e82610a23c46f6a3) (summary from search; the original was not opened)
- **Okoe, Jianu and Kobourov**, on a 258-node graph: node-link was more accurate on 5 of 10 topology tasks and less accurate on 2, with clustering tasks about equal — [arXiv 1709.00293](https://arxiv.org/pdf/1709.00293.pdf)
- **Large online experiment** (*Network Science*), networks of 20 and 50 nodes: node-link was faster and more accurate than two matrix forms, and the gap narrowed with practice — [Cambridge Network Science](https://www.cambridge.org/core/journals/network-science/article/understanding-nodelink-and-matrix-visualizations-of-networks-a-largescale-online-experiment/C293136C4761F09D4C2C328E2BC19287)
- **Filipov et al.**: matrices supported tasks on lower-level entities better, while animated node-link diagrams were the participants' favourite — [arXiv 2208.13716](https://arxiv.org/pdf/2208.13716v2)
- **Tactile study** with 8 blind and low-vision participants: node-link diagrams were preferred and better for paths and clusters, while an adjacency matrix or braille list was better for "are these two directly connected" — [arXiv 2003.14274](https://arxiv.org/abs/2003.14274)
- **Obsidian community.** A Reddit poll on navigating with the global graph got 302 votes: 178 never, 54 "rarely ever", 44 rarely, 23 frequently. The poll is anecdotal and self-selected — [r/ObsidianMD Dec 2024 (mirror)](https://reddit.birdcat.cafe/r/ObsidianMD/comments/1hg9qr3/how_often_do_you_use_the_global_graph_in_obsidian). Forum threads: [What's the point of the graph view?](https://forum.obsidian.md/t/whats-the-point-of-the-graph-view-how-are-you-using-it/71316), [How do you use the graph view?](https://forum.obsidian.md/t/how-do-you-use-the-graph-view/2785), [You all say the graph is useless…](https://forum.obsidian.md/t/you-all-say-the-graph-is-useless-let-me-show-you-how-to-use-it/116738), and a large-vault performance freeze even at depth 1: [forum](https://forum.obsidian.md/t/obsidian-graph-view-doesnt-work-for-a-large-vault/106287.md). A defence argues the graph helps judge how mature notes are — [Eleanor Konik](https://www.eleanorkonik.com/its-not-just-a-pretty-gimmick-in-defense-of-obsidians-graph-view)
- **Wikipedia previews** are the one large, controlled positive result for a linking technique (see the first section) — [Page_Previews](https://www.mediawiki.org/wiki/Page_Previews)

### Inferences
- With 4–20 nodes, the size of the series for the foreseeable future, the research favours node-link for following paths: "how does 0.3 get to paper 0?" That is the one task where a small graph can earn its place against a list. A matrix makes little sense at this size.
- The PKM complaints are about global graphs of hundreds of untyped notes. A small typed graph with a fixed layout (time or number order on one axis) is a different object, and the "useless" critique does not clearly apply to it.
- The site's WebGL node web on the landing page plays the "pretty global graph" role already. The archive should do the plainer job.

### Gaps
- Tufte's chartjunk page returned 403 to a script, so no Tufte citation was gathered. I found no CHI/UIST paper specifically on navigating literature graphs versus lists of a research series.

## Implementation notes for a vanilla-JS static site

### Takeaway
Every successful system read here builds its link data at build time (gwern's nightly backlink job, Quartz's `contentIndex.json`, blueprint's plasTeX pass) and keeps runtime JS small and lazy. Accessibility guidance comes down to always shipping the relationships as real HTML: lists or tables of links, plus per-node tables you can navigate. The graph is then an enhancement on top of crawlable text.

### Cited Findings
- **Build-time data.** Quartz's graph only works if the build emits `contentIndex.json` — [Quartz graph view](https://quartz.jzhao.xyz/features/graph-view). gwern generates backlinks offline and transcludes them lazily — [gwern.net/design](https://gwern.net/design). Blueprints derive the graph from `\uses` at build time — [leanblueprint](https://github.com/PatrickMassot/leanblueprint)
- **URL state.** Quartz stacked pages keep the stack in the hash (`#stacked=a,b`) — [Quartz stacked pages](https://four.quartz.jzhao.xyz/plugins/stackedpages)
- **Accessibility.** WCAG 1.1.1 requires a text alternative serving an equivalent purpose, and complex images need more support, such as a nearby data table with proper headers — [UNR accessibility guide](https://www.unr.edu/accessibility/resources/documents/accessible/research-and-publications/strategy-2); [UTS guide](https://educationexpress.uts.edu.au/collections/accessible-practice-for-maths-and-diagrams/resources/write-alternative-text-for-graphs-charts-and-diagrams/). An accessible Mermaid demo renders one table per node, whose edge column links to the connected node's table (Enter navigates) — [MermaidAccessDemo guide](https://samkacer.github.io/MermaidAccessDemo/guide). TADA (node-link diagrams for blind and low-vision users) — [arXiv 2311.04502](https://arxiv.org/html/2311.04502v4); Benthic (structures that follow the visual layout, not only adjacency) — [MIT Vis](https://vis.csail.mit.edu/pubs/benthic.pdf)
- **Hover delay.** Wikipedia lets admins set a dwell time; 250 ms is the documented example — [Page_Previews](https://www.mediawiki.org/wiki/Page_Previews)

### Inferences
- **Data.** Add per-page fields to `pages.meta.json`, which is already the single registry: `series` (for example "fractals"), `number` ("0.3"), `parent`, `uses` (a list of `{target: "slug#anchor", type: "reuses-code|reuses-figure|extends|cites"}`), and `status`. `site.py` would then emit (a) a static HTML "series" block in each paper inside generated markers, as `site.py nav` does for the INDEX panel, with parents, children and typed backlinks with section anchors; (b) a `series.json` for popups; (c) optionally an inline SVG graph rendered at build time, so it needs no JS and is crawlable. Layout: paper number on one axis, date on the other.
- **Runtime JS.** One small popup module (hover or long-press, about 250 ms delay, focus-triggered for keyboard users) that fetches the target's abstract or section from `series.json`, or transcludes the anchored section with `fetch` + `DOMParser`. Lazy, no framework.
- **Shared references.** One BibTeX-like source (papers/fractals already has `refs.py` numbering citations) can produce Distill-style hover citations and a "shared references" count per pair of papers. That count is the co-citation edge weight.
- **Accessibility and SEO.** The real navigation is the HTML list or tree. The graph should be `aria-hidden` or carry an alt summary, with a "view as table" fallback. This matches the repo rule that the WebGL INDEX map ships with a crawlable NAV block.

### Gaps
- I found no benchmark of popup or transclusion performance on mobile. I did not research gwern's popup code size or the details of its touch "popin" handling.
